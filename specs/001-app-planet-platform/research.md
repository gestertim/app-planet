## R-01 學生「帳號＋系統核發登入碼」身分驗證（規格要求：不得假設供應商原生支援）

> **D-07a 狀態（教育者 2026-10-21 決定）：已選首選驗證方案（方案 A），附實測條件。** 批准範圍僅限方案 A 的**研究與設計方向**；**尚未批准**技術驗證結果、登入碼長度／效期／限速數值、付費資源與 Plan 定稿。**不是「已驗證可上線」**：S-01～S-03 全部〔尚未執行〕。若驗證失敗，保留方案 B／C 與影響（見本節「方案 A 失敗時的替代與影響」）交教育者重新決定；**不得自行更換 Auth 供應商**。

**查證結論：Supabase Auth 不原生支援「username＋登入碼」。**

| 需求 | Supabase 原生？ | 官方依據（2026-10-21） |
| --- | --- | --- |
| 無電郵、無電話的帳號識別登入 | **否**。原生登入識別為 Email、Phone、OAuth／OIDC、SAML、匿名、Web3 | supabase.com/docs/guides/auth ；…/auth/passwords（「password connected to their email or phone number」） |
| 管理端建立使用者／改密碼／封鎖／撤銷／刪除 | **是**：`auth.admin.createUser`（`email_confirm`、`password`）、`updateUserById`（含 `ban_duration`）、`signOut`、`deleteUser` | …/reference/javascript/auth-admin-createuser；supabase/auth 原始碼 |
| 帳號維度登入限速 | **否**。`/auth/v1/token` 預設以 **IP** 限速（官方 2026-10-21 核對：預設 150 次／5 分鐘、突發至多 30 次，涵蓋密碼、refresh token 等授權類型）；`/auth/v1/verify` 預設 30 次／5 分鐘；只有「Password Verification Attempt Hook」可做嘗試層級攔截，且**僅 Teams／Enterprise** | …/auth/rate-limits；…/auth/auth-hooks |
| 停用後 JWT 立即失效 | **否（官方明述）**：`signOut` 撤銷 refresh token，但**access token 到期前無法撤銷**；access token 預設 1 小時，可調（官方建議不低於 5 分鐘）。**2026-10-21 補核**：管理端 `auth.admin.signOut(jwt, scope)` 的參數為「一個有效且已登入的 JWT」（Admin signOut 參考頁），即**以使用者 id 一次撤銷全部 session 的官方 API 本輪未查到**；Sessions 文件載明 session 可能因「使用者改密碼或執行敏感操作」而終止（「depending on configuration」，是否適用管理端改密碼**未查到**） | …/reference/javascript/auth-signout；…/auth-admin-signout；…/auth/sessions |
| JWT 與 session 對應 | 每個 access token 含 `session_id` claim，可對應 `auth.sessions` 主鍵（Sessions 文件）；**RLS／資料庫函式能否可靠讀取 `auth.sessions` 並據以拒絕已撤銷的 session：未查到，待 S-03 實測** | …/auth/sessions |
| 空閒逾時／時間盒 session | **Pro 以上**才有 | …/auth/sessions |
| 第三方／自訂 JWT 接 RLS | 有，但須**非對稱簽章＋OIDC Discovery**；**無法關閉原生 Supabase Auth** | …/auth/third-party/overview |
| 密碼強度／洩漏密碼檢查 | 最小長度與字元類型可設；HIBP 洩漏檢查 **Pro 以上** | …/auth/password-security |
| 合成電郵網域（如 `.invalid`）是否被拒 | **未查到明文**（原始碼僅見 RFC 格式驗證） | github.com/supabase/auth（internal/api） |

**可行方案比較**

| 方案 | 做法 | 優點 | 缺點／風險 | 評估 |
| --- | --- | --- | --- | --- |
| **A（首選驗證方案；教育者 2026-10-21 決定）合成電郵＋登入碼當密碼，BFF 代為登入** | 每位學生在 `auth.users` 建立**不代表真實學生電郵**、不可投遞的合成電郵（隨機 uuid 區段，僅作內部識別，不對外顯示、不寄信）；登入碼＝該帳號密碼；學生只在 App Planet 登入頁輸入「帳號（handle）＋登入碼」，由 **Next.js 伺服器端**把 handle 對應到合成電郵後呼叫 `signInWithPassword`；管理端以 `admin.createUser`／`updateUserById` 核發與重發 | 沿用已批准的 Supabase Auth（session、refresh、cookies、RLS 全部原生）；學生畫面仍只有帳號與登入碼，不收電郵／電話；學生不自設密碼；重發＝改密碼；停用＝`ban_duration`＋資料層閘門 | ① 官方無帳號維度限速 → **在 BFF 自建帳號＋IP 雜湊限速**；② 伺服器端呼叫 Supabase 時來源 IP 為託管平台出口 IP，Supabase 的 per-IP 限速（`/token` 預設 150／5 分）會讓全校共用額度 → 須轉送真實用戶端 IP：官方載明需**手動啟用 IP 轉送**、以 `Sb-Forwarded-For` 標頭搭配 **secret API key**（publishable 與舊版 anon／service_role 金鑰不支援），**待 S-02 實測**；使用 secret key 的呼叫須隔離於單一伺服器模組，且**不得以該高權限 client 沿用使用者 session**（SDK 行為待驗證）；③ 密碼規則須設為「最小長度＝碼長、不強制字元類型」；④ 合成網域相容性**未查到官方明文**，以 S-01 實測；⑤ 同一帳號被他人刻意輸錯會被鎖定（拒絕服務）→ 採「漸進延遲＋帳號×IP 雜湊雙鍵」而非硬鎖定；⑥ **新增（2026-10-21）**：官方 Admin signOut 需使用者有效 JWT，BFF 在重發或停用時未必持有 → 舊 session 的撤銷與資料層阻擋須經 S-03 驗證（候選機制見 quickstart §1.1） | **首選；附實測條件（S-01～S-03 尚未執行）** |
| B 自行驗證登入碼，再以 `admin.generateLink`＋`verifyOtp` 建立 session | 登入碼雜湊存自有表（argon2id）；通過後用 magiclink 流程換 session | 完全控制節流與雜湊；不佔用 Supabase 密碼欄位 | 流程繁瑣、仍受 `/verify` IP 限速；多一套憑證儲存要保護；（**未查證**該流程的官方保證） | 備選 |
| C 第三方 IdP（Clerk／Auth0）原生 username | Clerk 可啟用 username；Auth0 資料庫連線有 `username` | 原生支援 username | **更換已批准的 Auth 方案**，須走憲章 III 變更流程；教師／管理員也需遷移；新增供應商處理兒童資料的條款審查 | 不建議；僅在 A 實測失敗時提報教育者 |
| D 匿名登入＋自建對照 | `signInAnonymously` | 無電郵 | 匿名使用者每次新建身分，無法對應「帳號」與重發語意 | 不適用 |

**決定（教育者 2026-10-21）**：**D-07a 採方案 A 作為「首選驗證方案」**——在既有 Supabase Auth 基線內以管理 API 達成，不新增供應商。**狀態＝已選首選驗證方案，附實測條件**；不是「已驗證可上線」。實測條件為 quickstart S-01～S-03（合成資料；〔尚未執行〕）：合成電郵相容性、重發後舊登入碼失效、舊 access token／session 的資料層阻擋、同校共用網路下的節流、登入錯誤不洩漏帳號是否存在。**任一項失敗且無法在方案 A 內修正，即列出方案 B／C 與影響交教育者重新決定（FR-051）；Plan 不自行改採 B／C，不自行更換 Auth 供應商。**

**方案 A 失敗時的替代與影響（保留，供重新決定；以下皆未實測）**

| 失敗情境 | 方案 B（自驗登入碼＋`admin.generateLink`／`verifyOtp` 換 session） | 方案 C（Clerk／Auth0 username） |
| --- | --- | --- |
| 合成網域或合成電郵被拒（S-01） | 仍須有 `auth.users` 列與可用的 session 換發流程，合成電郵若被拒，B 同樣受影響，須先確認 | 不受影響（原生 username） |

**不論方案，皆須教育者重新決定後才可改動**；成本與時程影響於屆時另行估算。

**登入碼設計（碼長、格式、效期為〔待決 D-07〕；以下為有依據的建議值）**

| 項目 | 建議 | 理由 |
| --- | --- | --- |
| 熵 | **≥ 50 bits** | 線上猜測受限速；離線風險來自資料庫外洩時的雜湊（Supabase 以 bcrypt 保存）；50 bits 在合理成本下難以離線窮舉 |
| 格式候選 1 | 10 字元 Crockford Base32（排除易混字 `I L O U`），分 2 組顯示 `XXXXX-XXXXX`（50 bits） | 可大小寫不分、可印在卡片；對 G4–6 輸入較難 |
| 格式候選 2 | 5 個詞（自 1,024 詞的兒童適齡詞表挑選；5×10＝50 bits），以連字號分隔 | 較易記與輸入；詞表需教育者／教師審閱以避免不適詞（**詞表屬內容審閱事項**） |
| 效期 | 碼本身**無時間效期**，僅在「重發、停用、刪除、恢復後須重新核發」時失效；另設**首次領取期限**（核發後僅可顯示一次，逾期須重發）〔PP-02，建議 72 小時，待核定〕 | 課堂情境避免學生在不穩定的期限被登出；「效期」是否改為學期結束批次重發，列入 D-07 選項 |
| 一次性顯示 | 核發／重發當下回傳一次；之後不可讀；`Cache-Control: no-store`；日誌／稽核／通知／錯誤追蹤過濾 | FR-051 |
| 登入節流（參數〔PP-03〕，建議值待核定） | 帳號×IP雜湊：連續失敗 5 次後延遲 30 秒，之後每次翻倍，上限 15 分鐘；IP雜湊：每分鐘 20 次；全域：偵測突增時啟動人工開關 | 防暴力猜測並避免單一同學惡意鎖死他人；僅存 HMAC 雜湊（不存原始 IP） |
| 防列舉 | 未知帳號與錯誤碼回應與耗時一致（對未知帳號仍執行等價的雜湊工作）；學校「未確認」的學生僅在**憑證通過後**才收到「學校尚未完成啟用」說明 | UX 1.1「憑證未通過不洩漏帳號是否存在」；注意：憑證通過才提示會對「已知正確憑證」的人揭露學校狀態，屬已批准設計 |
| 交付學生的方式（〔待決 D-07〕） | 建議：核發／重發 RPC 回傳一次性顯示給**操作者**（發起教師或管理員），由其以列印卡片或當面交付；平台不寄送 | 學生無電郵／電話；不新增通知通道 |

## R-03 授權架構

**決定**：三層防線，缺一不可。
1. **資料層（主防線）**：所有表 RLS；授權判定用 `SECURITY DEFINER` 純函式（`account_gate`、`teacher_can_view_student`…，見 data-model §2）即時查表，**不信任 JWT claims**；角色／狀態／綁定欄位禁止客戶端更新，僅能經具名 RPC 變更。
2. **服務層**：Next.js Route Handler 使用**使用者身分的 Supabase client**（RLS 生效）；僅限列名的服務模組（Worker、排程清除、管理員 RPC、公開閘道）使用 service role，並在程式內以 `packages/core/policy` 重新檢查同一份規則（雙實作以同一張案例表驅動測試，防止漂移）。
3. **背景工作**：開始與每個重要步驟重新檢查（FR-038）；學校狀態用 `approval_epoch` 偵測（data-model §4.3）。

**理由**：憲章 V 要求伺服器端與資料存取層強制執行；Supabase 官方說明 access token 到期前無法撤銷，故不能以 JWT 為授權依據。**替代方案**：把 `status` 放進 custom access token claim——被拒，因為殘存期內會放行已停用者。

### 後續獨立 β2 feature 的研究紀錄（非 MVP 執行設計／不在本輪實作）

- **`stop()` 不可用於撤銷**：N=10／格，stop 後同一控制代碼再次呼叫 10/10 自動恢復；kill 只終止程序，沙箱仍在；delete 後 10/10 新呼叫拒絕（404）。撤銷不能只 stop；需平台 listing／epoch／grant 重驗及 delete。原始：[vc3e-raw.json](./spikes/security-boundaries/vc/results/vc3e-raw.json)。
- **呼叫端逾時不等於終止**：`AbortSignal` 中止後沙箱程序仍活著；逾時須明確 **kill/delete**（沙箱 timeout 為後備）。delete API p50 698 ms，但在途結束 p50 6,002／max 6,466 ms；不可把 API 返回時間當終止時間。完整下架→拒絕新呼叫的跨網路路徑未驗收。
- **不採恢復路徑**：p95 16.6 秒，每次 stop 產完整快照約 821 MB，30 次後累積 37 份約 30 GB、試用儲存 402；不是成本／延遲的解法。M 未被硬性判準推翻亦不表示可交付；不以暖共用狀態取巧，不啟動 W。
- 後續 feature 必須重新核定能力邊界、供應商資格／方案、配額、終止與撤銷上界、訪客隔離、課堂資源競爭及成本驗收；本次不建立 feature 文件、不宣稱其 Gate 通過。
